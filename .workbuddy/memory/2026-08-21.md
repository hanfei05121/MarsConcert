## ⚠️ 关键坑：每个歌目录只能留一个 .lrc
- `src/main/index.ts:215` 启动即 `scanLibrary()` 自动重扫；`scanner.ts:62` 取目录内 `files[0]`（第一个 `.lrc`）。
- 目录里若存在两个 `.lrc`（如 `绅士.lrc` + `orig.lrc`），`files[0]` 顺序不确定 → app 可能读到错误的 LRC，表现就是"歌词没匹配上"。
- `upsertSong` 重扫时**只更新** `lrc_path`，**不动** `lyric_offset`（不会清零）。
- 结论：保证每个歌曲子目录**仅有一个** `.lrc`；备份请改用 `.bak`/`.baked` 等非 `.lrc` 后缀。

## LF vs CRLF 不影响 LRC 解析
- 用户担心 orig.lrc 是 Unix(LF) 而自己用 Windows(CRLF) 导致时间戳不匹配 —— 这是误解。
- LRC 解析按行切分，换行符 `\n`/`\r\n` 都正常，时间戳提取不受影响。orig.lrc 是纯 LF，照样能正确解析。

## BUG 修复：飙升榜/歌单头像不显示 + 底部栏无头像
- 现象：歌手名正常（artist.txt 生效），但头像不显示；底部栏只有音符图标。
- 根因：`database.ts` 的 `getSongs` 用 `rows as Song[]` 直接把 DB 行（snake_case）强转 `Song`（camelCase），未做字段映射。
  `Song` 接口混用命名：`orig_path/accomp_path/lrc_path/create_time` 是 snake_case（恰好对得上），
  但 `lyricOffset`/`artistAvatar` 是 camelCase，DB 列是 `lyric_offset`/`artist_avatar` → 这两个字段永远 undefined。
  → `SongRow` 因 `artistAvatar` 为空只显示首字占位（看起来没头像）；`lyricOffset` 同理无法恢复（因已烤进 LRC 未暴露）。
- 修复：
  1. `src/main/database.ts`：新增 `rowToSong(row)` 显式映射（含 `lyric_offset→lyricOffset`、`artist_avatar→artistAvatar`），`getSongs` 改用 `rows.map(rowToSong)`。
  2. `src/renderer/main/components/BottomBar.vue`：`.thumb` 改为有 `artistAvatar` 时显示圆形头像 `<img>`，否则回退音符占位。
- 验证：`npm run build` 通过。注意：DB 里 `artist_avatar` 早已由扫描器写入 token，此修复在读取路径，重启 app 即可生效，无需重新扫描。
- 关键教训：`Song` 接口命名不规范（snake/camel 混用）是此 bug 根源；若日后统一成 camelCase 并配 DB 列改名迁移更彻底，但当前加 mapper 成本最低、风险最小。
